## 1. 文档目的

本文回答四个问题：

1. Fractal Art 最终是一个什么产品；
2. 用户如何从新建作品走到保存、恢复和导出，形成完整创作闭环；
3. Fractal Art、ImageLab、Workflow Studio 和 Host 各自负责什么；
4. 应当按照什么顺序逐步实现，且每个阶段结束时产品应当“长成什么样”。

本文不是数学教材，也不是具体类、方法和 AXAML 控件的最终设计。实现时可以调整内部命名，但不得随意改变已经发布的插件、Document、Action 和文件格式身份。

### 2.2 ImageLab 当前形态

ImageLab 当前是由多个独立 Persistable Document 组成的图像实验产品，已经覆盖调色板与颜色迁移、卷积、频域滤波、频谱艺术、梯度域融合、内容感知缩放等能力。

当前需要明确：

- ImageLab 已登记文件式 `apply-art-effects-file` Workflow Action；
- 首批共享核心包含确定性 Gaussian Blur、Bloom 和 Grain，不包含实时效果目录；
- Shared Domain 不引用 Avalonia、Workflow、JSON、DI 或文件系统；
- 两插件不共享 CLR DTO 或二进制库，只通过 File Artifact v1 描述对象交互。

因此，Fractal Art 把 ImageLab 视为可选的受治理文件处理 Provider，而不是可直接注入的效果引擎。

### 2.3 Workflow Studio 当前形态

当前 Workflow Studio 是 Workflow Action Consumer。它编辑、验证并顺序执行受 Host 治理的 Action 步骤，而不是一个可直接嵌入其他 Document 的实时像素节点图运行时。

当前 SDK 还存在以下边界：

- Host 已允许同一插件同时登记 Provider 和 Consumer，并过滤自有 Action、拒绝自调用与 Handler 嵌套调用；
- Action 输入输出通过 SDK、BCL 和 `JsonElement` 跨插件边界传递；
- 大型像素缓冲区、插件私有对象和 ViewModel 不应直接跨 ALC 传递；
- Workflow Studio 适合编排粗粒度、可治理、可记录的任务，不适合承担拖动参数时每帧触发的实时预览。

因此，本文把“作品内部创作管线”和“Host Workflow Action 编排”视为两个层次，不能混为同一个概念。

## 3. 产品定位

### 3.1 一句话定位

> Fractal Art 是一个以二维分形艺术创作为主、数学直觉展示为辅的生成艺术工作室；用户通过预设、变异、图层、颜色、图像效果和跨分形组合，将数学结构转化为可保存、可恢复、可导出的作品。

### 3.2 核心用户

- 希望快速得到分形视觉作品的普通创作者；
- 喜欢生成艺术、程序纹样、海报、壁纸和动态视觉的设计者；
- 对分形有兴趣，但不准备先学习完整数学理论的探索者；
- 希望通过 Workflow 批量生成、组合或后处理作品的高级用户。

### 3.3 产品优先级

优先级从高到低为：

1. 快速产生具有作品感的结果；
2. 通过 Seed、变异和参数锁定持续探索；
3. 保存完整创作配方并可靠恢复；
4. 通过图层、遮罩和效果形成非破坏性组合；
5. 用直观动画解释图形如何生成；
6. 允许高级用户通过 Workflow 批量或跨插件编排；
7. 扩充分形种类和更深的数学参数。

### 3.4 明确不做什么

Fractal Art 不以以下目标作为首要方向：

- 不提供严格数学证明或完整分形理论课程；
- 不承诺无限精度或科研级误差证明；当前提供有明确资源上限、可保存且可测试的 32–1024 位深度缩放；
- 不把每一种数学公式做成互不相关的独立页面；
- 不复制 ImageLab 的分析型 Document；
- 不在插件内重新实现一个与 Workflow Studio 竞争的通用工作流编辑器；
- 不为了展示技术能力而默认创建大量 Dock Tool。

## 4. 产品形态

### 4.1 一个核心 Persistable Document

产品默认只需要一种核心 Document：`Fractal Artwork Document`，中文显示名为“分形作品”。

每打开一个 Document，就代表一个独立作品。Document 拥有自己的：

- 画布尺寸和背景；
- 生成器与参数；
- Seed 和随机状态；
- 图层、遮罩和合成关系；
- 颜色、渐变和材质；
- 效果链；
- 变体收藏与创作历史；
- 数学透镜状态；
- 动画参数；
- 画布视角、选区和界面呈现状态；
- 保存、恢复、撤销、导出和关闭语义。

Document 应当从普通 `AddDocument` 演进为 Host 正式支持的 Persistable Document。持久化建立之前，不应把临时内存状态包装成“已经能够保存作品”。

### 4.2 Document 内部布局

建议的默认布局为：

```text
┌──────────────────────────────────────────────────────────────┐
│ 作品名  撤销/重做  Seed  生成变体  数学透镜  预览质量  导出   │
├────────────┬──────────────────────────────┬──────────────────┤
│ 创作导航   │                              │ 当前属性         │
│            │                              │                  │
│ 生成       │           作品画布           │ 形态             │
│ 造型       │                              │ 颜色             │
│ 图层       │                              │ 效果             │
│ 效果       │                              │ 数学参数         │
│ 动画       │                              │                  │
├────────────┴──────────────────────────────┴──────────────────┤
│ 变体候选 / 数学过程 / 动画时间线                             │
└──────────────────────────────────────────────────────────────┘
```

左右区域和底部区域属于当前 Document 的内部工作区，可以折叠，但不登记成 Host Tool。

### 4.3 Tool 策略

首个完整静态版本保持零 Tool。

只有同时满足“跨多个 Document、生命周期独立于当前作品、长期保持可见”时，能力才有理由成为 Tool。

后期唯一明确有价值的候选是 `Render Queue Tool`：

- 接收来自多个作品的高分辨率图片和动画任务；
- 在用户切换或关闭当前视图后继续显示任务状态；
- 提供进度、取消、失败原因、重试和打开输出位置；
- 由插件级 singleton 承担，而不是持有某个 Document 的可编辑状态。

图层、属性、预设、数学透镜、时间线和效果面板都不应成为 Tool。

### 4.4 Workbench Command 策略

局部按钮、拖动、图层操作、参数修改和变体选择继续使用 Document 内部命令。只有对整个工作台有稳定意义的用户意图才登记 Workbench Command。

模板的 `ApplyWorkbenchMessage` 不属于产品能力，应在正式开发开始时移除，而不是改变它的语义后继续复用原 ID。真实命令可以等语义稳定后再增加，例如：

- 导出当前分形作品；
- 生成一轮变体；
- 取消当前渲染。

这些命令是否进入菜单或快捷键，需要在对应阶段单独评审；首版不默认占用全局快捷键。

## 5. 用户创作闭环

完整闭环定义为：

```text
新建作品
→ 选择视觉方向或预设
→ 生成第一幅结果
→ 生成并筛选变体
→ 锁定喜欢的形态、颜色或效果
→ 图层组合与 ImageLab 后处理
→ 可选开启数学透镜理解生成过程
→ 保存作品配方
→ 导出静态图片或动画
→ 关闭并重新打开继续创作
```

只有当最后一步能够可靠回到此前作品状态，产品才算闭环。单纯“能够画出一张分形图片”不是闭环。

## 6. 创作能力详细说明

### 6.1 视觉入口

默认入口按照视觉意图组织，而不是先要求用户理解数学分类：

- 植物与生长；
- 无限与花朵；
- 星云与粒子；
- 几何与纹样；
- 流体与扭曲；
- 玻璃与金属；
- 墨迹与纸张；
- 梦境与反馈。

高级入口再按照数学家族组织：

- 递归几何；
- L-System；
- 逃逸时间分形；
- 收敛域与根分形；
- IFS 与 Fractal Flame；
- 奇异吸引子；
- 随机生长；
- 分形噪声；
- 图像递归与反馈。

### 6.2 生成器家族

#### 递归几何与路径

包括分形树、科赫曲线、谢尔宾斯基结构、龙形曲线、递归圆和递归多边形。其核心输出应优先保留为路径或结构数据，便于描边、填充、矢量导出和层级动画。

#### L-System

提供经典预设和可视化规则编辑。默认参数使用“长度、分叉、角度、层级、随机度”等创作语言；文本规则和符号解释放在高级区域。

#### 逃逸时间分形

包括 Mandelbrot、Julia、Multibrot、Burning Ship、Tricorn 等。除了最终颜色，还应保留迭代值、距离估计、内部/外部遮罩和可选轨道信息。

#### 收敛域分形

包括 Newton、Halley 和 Nova。重点呈现花瓣、玻璃、晶体和窗花式结构，并用根归属、收敛速度等信息驱动颜色。

#### IFS 与 Fractal Flame

输出点云或密度场，支持仿射变换、概率、非线性 variation、对数密度和颜色累积。它是星云、火焰、烟雾和丝线质感的重要来源。

#### 奇异吸引子

包括 Clifford、De Jong、Hopalong、Ikeda 等，输出可重复的点云或密度场，适合长曝光、粒子流和发光线条。

#### 随机生长

包括随机分形树、DLA、裂纹、闪电和海岸线。所有随机过程必须受显式 Seed 控制。

#### 分形噪声与反馈

包括 fBm、Ridged Noise、Turbulence、Domain Warp、万花筒、Droste 和图像反馈。反馈循环应在运行时能够控制迭代次数和资源预算，不允许出现无法取消的无限执行。

### 6.3 艺术化参数与数学参数

默认向用户展示艺术化参数：

- 细节；
- 密度；
- 卷曲；
- 分叉；
- 对称；
- 拉伸；
- 边界锋利度；
- 流动；
- 扭曲；
- 发光；
- 颗粒感。

高级区域再展示对应数学参数：

- Iterations；
- Bailout；
- Exponent；
- Complex Constant；
- Recursion Depth；
- Affine Transform；
- Convergence Threshold；
- L-System Rules。

艺术化参数不是一套独立状态，而是对底层真实参数的稳定映射，保存和撤销时必须保持单一事实来源。

### 6.4 Seed、变体与参数锁定

“生成变体”是产品的核心交互，而不是附属随机按钮。

每轮可以生成 9 到 12 个候选，并支持：

- 调整变异强度；
- 锁定 Seed；
- 锁定构图；
- 锁定分形公式；
- 锁定颜色；
- 锁定效果；
- 只改变形态；
- 只改变质感；
- 收藏候选；
- 从收藏结果继续变异；
- 恢复某次候选为当前作品。

生成器和效果参数需要声明是否允许变异、取值范围、分布、步长和所属参数组。不能对所有数值简单做无边界随机。

### 6.5 图层、遮罩与组合

作品最终支持以下图层：

- 分形生成图层；
- 图像图层；
- 颜色/渐变图层；
- 调整图层；
- 遮罩；
- 分组；
- 背景；
- Master Effects。

支持的组合方式包括：

- 一个分形作为另一个图层的遮罩；
- 使用噪声扭曲 Julia 坐标；
- 使用分形树路径散布粒子或图案；
- 使用吸引子密度控制发光；
- 使用逃逸距离控制描边或材质；
- 将 Fractal Flame 填入递归几何；
- 将最终图像反馈回有限次数的递归采样。

### 6.6 颜色、材质与 ImageLab 效果

Fractal Art 负责结构和创作编排，ImageLab 适合提供可复用的无 UI 图像处理能力。优先级建议为：

1. 渐变映射与调色板；
2. 色彩调整与颜色迁移；
3. Blur、Glow 和 Bloom；
4. 位移、扭曲和液化；
5. 混合模式与遮罩处理；
6. 边缘、浮雕和法线效果；
7. 颗粒、纸张、胶片和画布纹理；
8. 色差、色散和镜头效果；
9. 频域风格化和图像反馈。

其中“调色板与颜色迁移、卷积、频域处理”等与 ImageLab 当前能力有现实交集；Bloom、Glow、通用位移和颗粒等仍是待建设能力，不能写成已经可调用。

效果必须是非破坏性的。改变后处理效果时，不应强制重新计算未受影响的分形生成节点。

### 6.7 数学透镜

数学透镜是 Document 内的一种观察模式，不是独立 Document 或 Tool。

它提供：

- 递归几何从第 0 层到第 N 层的构造过程；
- L-System 替换规则和绘制动作高亮；
- 逃逸分形单点轨迹、逃逸次数及颜色来源；
- IFS 每次选择的变换和点云形成过程；
- 吸引子轨迹从初始点逐渐稳定的过程；
- 参数变化和画面变化的直观对应。

数学透镜以动画、标注和通俗说明为主。公式只解释当前画面所需的最小概念，不扩展为严格证明系统。

### 6.8 动画与生产输出

后期支持：

- 分形生长；
- 参数关键帧；
- Julia 常量漫游；
- 无限缩放；
- 颜色流动；
- 吸引子形态变化；
- 效果强度动画；
- 可控循环；
- 静态高分辨率分块渲染；
- PNG、透明 PNG、序列帧和视频输出。

动画预览和最终输出必须使用同一份作品定义与求值规则，不能维护第二套动画实现。

## 7. 内部创作管线与 Workflow Action 的关系

### 7.1 作品内部管线

Fractal Artwork 需要一套可序列化的内部创作图或等价的有向处理模型：

```text
Generator
→ Geometry / Field / Point Data
→ Colorization
→ Image Effects
→ Layer Composition
→ Preview / Export
```

它主要服务于：

- 实时预览；
- 局部重算；
- 缓存；
- 撤销和重做；
- 非破坏性编辑；
- 参数动画；
- 作品保存和恢复。

这套内部模型可以先由 Fractal Art 私有实现，但应保持节点/步骤边界清晰，避免把算法、视图和 Document 状态揉在一起。它不等同于当前 Host 的 Workflow Action 定义。

### 7.2 当前可落地的 Workflow 方案

在现有 Provider/Consumer 互斥约束下，推荐的最终角色是：

```text
Fractal Art        → Workflow Action Provider
ImageLab           → Workflow Action Provider（由 ImageLab 独立演进）
Workflow Studio    → Workflow Action Consumer
```

Workflow Studio 可以编排粗粒度步骤：

```text
Fractal Art：根据作品配方渲染
→ ImageLab：执行某项可治理的后处理
→ Fractal Art 或其他输出能力：导出/归档
```

Fractal Art Document 内部的实时效果不应通过 Workflow Action 每次跨插件调用。原因是实时像素处理频率高、数据量大，而且当前 Action 通过 JSON 契约跨边界。

### 7.3 ImageLab 的两种复用方式

#### 方式 A：共享无 UI 算法包

将适合实时创作的算法抽成独立、可测试、无 Avalonia UI 依赖的共享包，由 Fractal Art 和 ImageLab 分别引用。该方式适合：

- 调色板提取；
- 颜色空间转换；
- 卷积；
- 渐变映射；
- Blur/Bloom 等像素效果；
- 分形 Document 内的实时预览。

插件之间不直接传递私有对象；各插件在自己的 ALC 内使用同一算法包版本。

#### 方式 B：Workflow Action 粗粒度编排

ImageLab 将稳定能力登记为受治理 Action，Workflow Studio 使用文件、受控资源引用或未来 Host Artifact 身份衔接步骤。该方式适合：

- 批量后处理；
- 长时间运行的分析或变换；
- 可记录、可确认的跨插件任务；
- 不要求拖动参数实时返回的处理。

禁止把大型图片编码进普通 JSON 参数。若 Host 尚无正式 Artifact 交换契约，应推迟跨插件大型图像工作流，而不是私自约定不可治理的临时路径协议。

### 7.4 未来 Workflow Studio 深度编辑

只有当平台提供适合创作图的稳定共享契约后，才考虑“在 Workflow Studio 中打开当前作品内部图”。在此之前可以优先开放粗粒度 Action，例如：

- `render-artwork`；
- `render-variations`；
- `export-artwork`；
- `inspect-artwork-metadata`。

不得在文档或 UI 中承诺当前 Workflow Studio 已经能够无损编辑 Fractal Artwork 的内部图。

## 8. 运行时与质量要求

### 8.1 确定性

同一版本的生成器在相同画布、参数和 Seed 下应得到一致结果。所有随机源必须来自显式上下文，禁止在算法内部临时使用不可追踪的随机种子。

### 8.2 异步与取消

渲染必须可等待、可取消。用户连续拖动参数时，旧请求要及时失效，不能在后台形成渲染队列。

### 8.3 渐进式预览

建议采用：

```text
交互中的低成本预览
→ 停止操作后的精细预览
→ 明确触发的最终导出
```

界面反馈要及时，但不能用低质量预览冒充最终导出结果。

### 8.4 局部重算与缓存

改变 Bloom 不应重新计算 Julia 迭代；改变某个上层图层也不应让不相关图层失效。缓存键至少考虑算法版本、参数、Seed、输入身份、尺寸和质量等级。

### 8.5 资源预算

递归层级、迭代次数、点数、反馈次数、图像尺寸和动画帧数都需要显式上限与取消检查。不能依赖 UI 限制替代领域层防御。

### 8.6 版本与迁移

作品格式、生成器、效果和预设都需要版本。旧版本打开时要么确定迁移，要么明确拒绝并保留原文件，不能静默改变作品。

### 8.7 缺失能力

作品引用未安装效果或未知节点时，应当：

- 仍能打开作品；
- 标记缺失能力和所属插件；
- 保留未知配置，避免保存时破坏；
- 禁止输出错误结果冒充正常渲染；
- 在能力恢复后允许重新求值。

- 允许 Julia/Mandelbrot 的原始 ScalarField 驱动另一个图层或组的遮罩；
- 建立图层级撤销、缓存、保存和缺失能力处理；
- 为复杂作品提供安全的资源预算。

**阶段形态**

用户可以组合 Julia 背景、递归树前景和整体发光/调色效果，形成真正的多层作品。

**完成标准**

- 图层顺序和混合结果可保存恢复；
- 隐藏图层不会继续无意义渲染；
- 删除被引用图层时给出明确处理；
- 遮罩和数据场有明确尺寸/坐标转换规则；
- 两个 Document 的图层和缓存完全隔离。

### G0010：数学透镜

### G0012：Workflow Action Provider

**目标**

在 G0007 首个 Render/Release Action 基础上扩展批量渲染能力，而不把实时创作管线变成跨插件 JSON 像素流。

**实施内容**

**阶段形态**

三条链路分别验证标量场、路径和点云，能够较早发现数据模型是否被某一种分形错误绑死。

## 12. 每个阶段共同使用的完成门禁

每个 `Gxxxx` 阶段至少检查：

1. **领域测试**：算法、参数、Seed、迁移和错误边界；
2. **Document 测试**：实例隔离、初始化、取消、Dirty、保存和关闭；
3. **注册测试**：Descriptor、稳定身份、Document/Tool 数量和命令归属；
4. **Standalone 验证**：真实 View、绑定、主题和插件自身对象图；
5. **性能验证**：交互预览、取消、内存和缓存失效；
6. **干净部署验证**：插件目录不存在开发期残留；
7. **正式 ZIP 验证**：交付物由 Build 生成；
8. **真实 Host 验证**：Document Scope、Dock、持久化、关闭、ALC 和跨插件协议。

Standalone、单元测试和真实 Host 验收互不替代。任何阶段若没有完成其声明的门禁，应标记为未封板，而不是通过降低措辞把缺失验证解释为完成。

## 13. 最终产品判断标准

当用户能够完成以下操作时，Fractal Art 才是一个闭环产品：

1. 在 Host 中新建“分形作品”；
2. 从视觉预设获得第一幅结果；
3. 生成多个变体并锁定喜欢的部分；
4. 添加第二种分形或图像图层；
5. 使用非破坏性颜色和效果塑造质感；
6. 使用数学透镜理解当前作品的生成过程；
7. 保存并关闭作品；
8. 重新打开后完整恢复配方和视觉结果；
9. 导出指定尺寸的静态作品；
10. 在不理解 Workflow 的情况下完成以上全部操作；
11. 在需要批量和跨插件处理时，再由 Workflow Studio 组合受治理 Action；
12. 在进入动画阶段后，将长任务交给 Render Queue 而不阻塞其他作品。

产品的核心价值不是拥有最多公式，而是让有限的生成内核通过变体、图层、颜色、ImageLab 算法和跨分形组合产生大量具有作品感的结果。
